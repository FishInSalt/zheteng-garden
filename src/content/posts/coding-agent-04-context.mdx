## 1. 为什么需要上下文管理？

前面几章中，Agent 把用户的任务交给模型，执行模型提出的工具调用，再把结果带到下一次模型调用中。每次调用时，提供给模型参考的信息，就叫作**上下文**。它既包括用户要求、历史对话和工具结果，也包括系统指令、项目约定和工具说明。

这些信息怎样帮助模型继续工作？假设我们给 Agent 一个任务：

> 修复求和函数：sum(2, 3) 返回了 23，预期结果是 5。保持公共接口不变，并运行测试验证。

第一次调用时，模型知道任务要求，但还没看到代码。Agent 根据模型的工具调用读取函数和测试，把文件内容带到下一次调用中。修改代码并运行测试后，普通用例通过了，负数用例却仍然失败；下一次调用还需要带上修改过程和测试结果，模型才能继续排查。

最直接的做法，是每次调用模型时，都把完整历史一起发过去。任务较短时，这样做简单有效：模型既能看到最初“不改公共接口”的要求，也能知道已经改过什么、测试出了什么问题。

但随着任务持续推进，这种做法会遇到两个问题。

**首先，模型的上下文容量有限。** 模型一次能处理的信息有上限，这个容量叫作“上下文窗口”，通常用 Token 计量。例如，Claude Sonnet 4.5 的上下文窗口为 20 万 Token，Sonnet 4.6 为 100 万 Token。

100 万 Token 大约能装多少内容？Google 将它粗略类比为 5 万行代码，每行约 80 个字符，实际占用会因内容和分词方式而异。

因此，随着任务推进、历史不断增长，Agent 无法一直把全部历史发给模型，需要控制每次提供的信息量。

**其次，模型利用长上下文的能力也有限。** 即使内容没有超过容量上限，模型也未必能准确找到并使用其中的全部关键信息。研究发现，在所测试的模型和任务中，同一条关键信息放在长输入的不同位置，会影响回答表现。[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)

回到修复任务，大量代码和测试日志累积后，模型可能遗漏最初“不改公共接口”的约束，或没有找到与当前错误相关的线索。这不意味着上下文越多，回答就一定越差：补充相关代码和错误信息通常有帮助。需要关注的是，提供的内容能否帮助模型判断下一步该做什么。

因此，Agent 需要随着任务推进，为每次模型调用组织和更新上下文信息，这就是**上下文管理**。本章要弄明白的是：**怎样准备足够、相关且放得下的上下文信息，让模型能够继续完成任务？**

## 2. 上下文怎样组织，并随着任务推进更新

回到修复求和函数的任务。模型要决定下一步做什么，需要知道用户要解决什么、应遵守哪些约束、有哪些工具可用，以及任务进行到了哪里，例如已经读取的代码、完成的修改和最新测试结果。

下面沿着一次模型调用，先看这些内容怎样组成上下文，再看历史增长后怎样检查长度、生成摘要，并用于下一次调用。

### 2.1 发给模型的上下文有哪些，分别从哪里来？

第 02 章介绍过，模型服务通过 API 接收输入。我们可以把所有内容拼成一段文字，但仍需要说明哪些是行为要求，例如“修改文件前先读取内容”，哪些是用户的任务，哪些是读取文件或运行测试得到的结果。同一句话出现在用户要求中，还是出现在工具读到的文件里，含义可能完全不同。

模型 API 提供消息角色和内容类型，用来标明这些信息的来源和用途；工具定义则通过规定的结构提供名称、用途和参数规则，让模型服务支持相应的工具调用。这样，Agent 可以按接口约定组织输入，不必把所有区别都放在一段文字里解释。

以 OpenAI 的 Chat Completions API 为例，`messages` 携带消息，通过 `role` 区分行为要求、用户输入、模型回复和工具结果：行为要求使用 `system` 或 `developer` 角色，具体取决于所选模型；用户输入、模型回复和工具结果分别使用 `user`、`assistant` 和 `tool`。工具定义则放在独立的 `tools` 字段中。[OpenAI API 文档](https://developers.openai.com/api/reference/cli/resources/chat)

imp 内部将系统指令单独保存在 `system`，对话历史放在 `messages`，可用工具放在 `tools`。它的 Chat Completions 适配器再把 `system` 转成一条 `role: "system"` 的消息，放入发给服务的 `messages` 中。因此，下面的三个字段是 imp 的内部组织方式，不是 Chat Completions API 的三个同名顶层字段：

```ts
// 文件：src/provider/types.ts
// 模块级接口：LLMRequest
// 节选：省略模型配置、输出上限、思考配置和中断信号。
export interface LLMRequest {
  system: string;
  messages: AgentMessage[];
  tools: Tool[];
}
```

用户提出的“不改公共接口”保留在用户消息中，也就是 `messages`；它不会因为是一条约束，就自动移到 `system`。

以项目约定为例，imp 在 [`runner.ts`](https://github.com/FishInSalt/imp/blob/main/src/runner.ts) 中把它加入 `system`：

```ts
// 文件：src/runner.ts
// 所在函数：RunnerImpl.assembleSystem
// 节选：省略加载提示和扩展提供的上下文段落。
let system = buildSystemPrompt(defaultSystemPromptContext());
if (!this.options.noContextFiles) {
  const context = loadContextFiles(this.options.cwd);
  if (context) {
    system += `\n\n# Project context (AGENTS.md)\n\n${context.text}`;
  }
}
```

`buildSystemPrompt` 提供基础指令和运行环境；`loadContextFiles` 读取项目约定。当前实现先查找 `~/.imp/AGENTS.md`，再从根目录到工作目录依次查找沿途的 `AGENTS.md`，把找到的内容拼接起来。因此，用户可以在项目根目录添加 `AGENTS.md`，写明编码规范、测试方式等要求，供 Agent 执行任务时遵循。

这些约定由用户或项目维护者编写，Agent 负责加载；规则冲突和信任边界留到第 07 章讨论。

`messages` 对应 Agent 循环使用的消息历史数组 `history`。

`tools` 在调用模型前准备好，工具注册和说明怎样交给模型，已在第 03 章介绍。

随着任务推进，模型回复、读取到的代码和测试输出不断加入 `history`。这些历史会在后续调用中再次发送给模型，占用的上下文空间也越来越多。前面提到，模型的上下文窗口有限，也未必能充分利用长上下文中的信息。因此，接下来需要解决的是：怎样控制历史长度，同时保留继续完成任务所需的信息？

### 2.2 历史越来越长，怎样管理？

当前主流的 Coding Agent 通常会结合多种手段管理上下文。例如，Claude Code 按需加载工具说明，并让子代理在独立上下文中工作，减少主对话积累的内容；历史接近上限时，先清理较早的工具输出，必要时再总结对话。[Claude Code 官方说明](https://code.claude.com/docs/en/how-claude-code-works#when-context-fills-up) Gemini CLI 也支持用摘要替换对话历史，减少后续调用占用的 Token。[Gemini CLI 官方说明](https://geminicli.com/docs/reference/commands/#compress) 这些做法的共同目标，是用更少的内容保留任务进展和关键依据，让模型能够继续工作。压缩结果不一定是文字摘要，例如 OpenAI 的压缩接口会返回模型可继续使用的非明文压缩内容。[OpenAI 官方说明](https://developers.openai.com/api/docs/guides/compaction)

这些方案既会控制进入上下文的信息量，也会整理已经积累的历史。对于不断增长的历史，一种常见处理方式是**上下文压缩**：用更少的内容保留继续任务所需的信息。下面看看 imp 怎样压缩历史、什么时候触发，以及压缩后怎样继续调用模型。

**怎样压缩历史**

imp 采用的是“较早历史生成摘要、近期消息保留原文”的方式。压缩入口 `compactAndSplice` 通过 `compactSession` 调用 `compactHistory`，由后者完成历史切分和摘要生成。

切分时要保留一段近期消息的原文，因为其中可能包含正在处理的代码和最新错误。

`compactHistory` 先用 `findCutIndex` 决定切分位置，再把历史分成两段：

```ts
// 文件：src/core/compaction.ts
// 所在函数：compactHistory
// 节选：settings 已准备好，省略前面的用量估算。
const cut = findCutIndex(args.messages, settings.keepRecentTokens);
if (cut <= 0) return null; // 没有适合移入摘要的旧消息。
const toSummarize = args.messages.slice(0, cut);
const retainedTail = args.messages.slice(cut);
```

`keepRecentTokens` 表示希望保留多少近期内容，是近似目标。`findCutIndex` 从后往前累计长度，达到目标后，继续向前寻找 `user` 或 `assistant` 消息作为保留段的起点。

为什么不能停在任意消息上？假设最后两条消息是：

| 消息     | 内容                                  |
| -------- | ------------------------------------- |
| 模型回复 | 调用 `bash` 运行测试，调用 ID 为 `t7` |
| 工具结果 | `t7` 的测试输出，负数用例失败         |

如果只保留第二条，就剩下一个失去对应调用的工具结果。切分需要尊重消息关系；这个例子应连同前面的模型回复一起保留。当前实现按消息角色寻找边界，不是在这一步重新判断每条内容的相关性。

切分后，`serializeForSummary` 把旧消息整理成带角色说明的文本，`compactHistory` 再单独调用模型生成摘要。这次调用不提供工具，系统指令要求只输出摘要，不继续执行原任务。

摘要要用于后续工作，因此不能只写“读了文件、修改了代码、跑了测试”。它需要交代原任务的要求、已经取得的进展，以及接下来继续处理所需的依据。源码中的 `SUMMARIZATION_PROMPT` 明确规定了这些内容：

```ts
// 文件：src/core/compaction.ts
// 模块级常量：SUMMARIZATION_PROMPT
// 节选：省略开头的任务说明，保留摘要格式与信息保留要求。
const SUMMARIZATION_PROMPT = `Use this EXACT format:

## Goal
[What is the user trying to accomplish? Can be multiple items.]

## Constraints & Preferences
- [Any constraints, preferences, or requirements mentioned by the user]
- [Or "(none)" if none were mentioned]

## Progress
### Done
- [x] [Completed tasks/changes]

### In Progress
- [ ] [Current work]

### Blocked
- [Issues preventing progress, if any]

## Key Decisions
- **[Decision]**: [Brief rationale]

## Next Steps
1. [Ordered list of what should happen next]

## Critical Context
- [Any data, code references, or facts needed to continue]
- [Or "(none)" if not applicable]

Keep each section concise. Preserve exact file paths, function names, and error messages.`;
```

这里分别要求保留目标、约束、进展、关键决策、下一步和必要上下文。放到修复任务中，“不改公共接口”应进入约束；已经找到的文件和完成的修改属于进展；文件路径、函数名和仍有用的错误信息，需要尽量准确保留。只有操作经过，没有这些细节，模型仍然不知道怎样接着做。

这些要求只作用于送去总结的旧消息，最新测试结果仍保留在近期消息中。提示词不能保证摘要保留了所有必要信息；需要精确使用的代码和错误信息，仍应保留原文，必要时重新读取。

**什么时候触发压缩**

需要先估算当前上下文占用了多少 Token，再判断剩余空间是否充足。除了输入中的系统指令、工具说明和消息历史，还要为模型生成回复留出空间。imp 在 [`compaction.ts`](https://github.com/FishInSalt/imp/blob/main/src/core/compaction.ts) 中用下面的条件判断是否触发压缩：

```ts
// 文件：src/core/compaction.ts
// 省略参数类型。
export function shouldCompact(contextTokens, settings) {
  return contextTokens > settings.contextWindow - settings.reserveTokens;
}
```

`contextWindow` 是所选模型的窗口配置，`reserveTokens` 是提前留出的余量。它不是每次请求的 `maxTokens`：后者限制这一次生成的输出，两者需要配合设置。

用一组简化数字看这个判断。下面的 32,000 和 8,000 仅用于演示，不是 imp 的默认配置：

| 时刻                                | 估算占用     | 压缩阈值                | 判断                 |
| ----------------------------------- | ------------ | ----------------------- | -------------------- |
| 测试前                              | 20,000 Token | 32,000 − 8,000 = 24,000 | 还没触发压缩         |
| 加入一份约 6,000 Token 的测试输出后 | 26,000 Token | 24,000                  | 下一次调用前尝试压缩 |

`contextTokens` 由 `estimateContextTokens` 估算：优先参考最近一次模型调用返回的用量，再估算之后新增消息的长度；没有可用的用量记录时，就根据消息内容估算。

估算并不等于准确计数。当前 imp 对未测量的内容采用字符数除以 4 的近似方法，首次估算也没有单独计入系统指令和工具说明。因此，这个判断只能帮助提前触发压缩，仍需要处理模型服务返回的超限错误。生成摘要本身也需要调用模型，应提前预留空间，不能等上下文完全装不下时才处理。

长度检查放在每次模型调用前。Agent 循环通过 `onBeforeTurn` 留出检查和整理历史的位置；处理完成后，再把当前的 `history` 交给模型。下面节选自 [`loop.ts`](https://github.com/FishInSalt/imp/blob/main/src/core/loop.ts)，省略类型和非主线分支，不能单独运行：

```ts
// 文件：src/core/loop.ts
// 所在函数：runAgentLoop
// 位于循环内；省略前面的中断检查和用户追加消息处理。
await onBeforeTurn?.(history); // 调用前检查，必要时更新历史。

const assistant = await streamAssistant({
  provider,
  request: { system, messages: history, tools, model, maxTokens, thinking, signal },
  onEvent,
  usage,
});
// 后续：保存模型回复，执行工具，再把结果加入 history。
```

调用方通过 `onBeforeTurn` 接入自动压缩。下面节选 `RunnerImpl.runTurnInner` 传给 `runAgentLoop` 的回调，保留自动压缩开关与触发条件：

```ts
// 文件：src/runner.ts
// 所在函数：RunnerImpl.runTurnInner
// 节选 runAgentLoop 的 onBeforeTurn 配置；省略其他配置和错误提示包装。
onBeforeTurn: session
  ? async (history) => {
      if (!this.autoCompact) return;
      const est = estimateContextTokens(history);
      if (!shouldCompact(est.tokens, settings)) return;
      await this.compactAndSplice(provider, settings, model);
    }
  : undefined,
```

这条自动压缩路径要求有会话且开启自动压缩。没有触发阈值时，历史保持原样；触发后，才进入 `compactAndSplice`。用户新要求和上一轮工具结果已经加入历史，因此检查针对的是即将用于下一次调用的信息。

**压缩后，怎样继续调用模型**

`compactHistory` 返回摘要和保留段后，`compactSession` 将它们记录为一次压缩结果。`session.buildContext()` 据此重新组织消息，`compactAndSplice` 再更新正在使用的 `history`：

```ts
// 文件：src/runner.ts
// 所在函数：RunnerImpl.compactAndSplice
// 节选：省略 session 的获取与空值检查、思考配置和界面提示。
const compacted = await compactSession({ session, provider, model, settings });
if (compacted) {
  this.history.splice(0, this.history.length, ...session.buildContext().messages);
}
return compacted !== null;
```

只有成功生成摘要并取得压缩结果后，才会更新历史；失败时保留原来的消息。

`splice` 在原数组上更新内容，因此前面 Agent 循环中的 `messages: history` 随后取得的就是摘要和保留的近期消息。系统指令和可用工具仍通过 `system`、`tools` 提供，这次历史压缩没有改变它们。

摘要会被包装成带有“这是之前对话的总结”标记的消息，后面接上保留的近期消息。这里变短的是本次模型输入，原始会话记录仍然保留；历史怎样落盘和恢复，第 05 章再展开。

## 4. 这次看什么，与下次怎样恢复

上下文管理贯穿每次模型调用：提前提供必要规则，执行中按需补充信息，历史过长时保留继续工作所需的事实，并将较早的过程整理成摘要。

任务继续推进，模型看到的消息可能已经从完整历史变成了摘要和近期记录。关闭终端后再打开，怎样恢复同样的工作状态？那些没有放进本次上下文的原始消息，又保存在哪里？第 05 章接着看会话与持久化。
