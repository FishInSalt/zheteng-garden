AI 模型的能力越来越强，它们也通过各种工具进入了实际工作。对我来说，Coding Agent 是一个很直接的例子：提出目标之后，它可以搜索代码、修改文件、运行测试，再根据结果继续处理问题。

我希望进一步理解，这些动作是怎样被组织起来的。于是，我开始参考 pi，从零开发一个属于自己的终端编程助手：**imp**。

这个系列会记录我实际做了哪些工作，也会逐个拆开核心模块，解释开发一个 Coding Agent 需要解决哪些问题。本文先交代背景，再给出系统全貌、开发路线和阅读目录。

## 为什么想自己做一个 Coding Agent

现有产品已经展示了很强的能力，但在自己的使用过程中，我也遇到了一些不合意的地方。

对我这样的国内用户来说，Claude Code 的使用门槛让我觉得不够友好；使用 Codex 时，我又希望对推理过程有更多可见性，而产品提供的展示没有完全满足我的需求。我接触到的一些国产工具，有的设计大量沿用一线产品，有的实现还比较简陋，暂时没有找到完全符合自己偏好的选择。

这些使用体验，让我开始关注模型之外的那层程序：它怎样组织信息，怎样调用工具，又怎样把执行过程呈现给用户？如果可以自己掌握这一层，我就能按照自己的需求调整工作方式。

这类围绕模型、支持它持续执行任务的运行机制，通常被称为 **harness**。在这个系列中，可以先把它理解成：**把模型、工具、上下文和任务状态组织在一起的程序。**

我想做 imp，有两个相互联系的目标：

- **加深对 AI Agent 的理解。** 亲手实现各个环节，弄清楚它们各自解决什么问题，以及组合起来之后会产生哪些新问题。
- **做一个自己用得上的工具。** 用 imp 辅助处理真实任务，再把使用中遇到的问题带回开发过程。

模型会提供哪些内容，由模型服务本身决定；自己的 harness 可以控制如何组织和展示已经返回的信息。对过程的可见性，也包括工具调用、参数、执行结果、错误和上下文变化。

## 为什么选择 pi 作为参考

[pi](https://github.com/earendil-works/pi) 吸引我的地方，是它的简洁与很强的自定义能力。我希望借助这样的参考，理解一个编程助手的核心怎样成立，以及新能力应该接在什么位置。

imp 的项目计划也沿着这个思路展开：先完成一个能够执行任务的最小版本，再逐步加入工具、会话、交互与扩展。这样，每一层复杂度都有具体的问题作为起点。

“从零开发”在这里指自己实现 imp 的核心运行逻辑、工具、状态管理和接入方式。当前项目使用 TypeScript 与 Node.js，终端 UI 复用了 pi 的组件库。参考已有设计和复用基础组件，也是开发过程中的选择；后续章节会说明哪些部分自己实现，哪些部分借鉴或复用。

## 一次任务里，这些部分怎样配合

先看一个用于说明机制的任务：**“修复求和函数的错误，并运行相关测试。”** 这不是某次真实执行的回放，只用于建立整体流程的直觉。

<TaskOverview />

在这个过程中，模型依据当前收到的信息提出下一步，运行程序执行相应动作，并把观察到的事实交回模型。一次用户请求，可能因此变成多次模型调用。

如果修改失败，错误结果也会成为后续决策的信息。如果测试通过，测试输出可以作为验证证据。模型最后的文字总结，需要与这些执行记录相互印证。

01 章会把这段流程缩成最小伪代码，说明一个 Agent Loop（代理循环）究竟需要哪些步骤。

### 让动作真正发生：模型接入、执行循环与工具

**模型接入**负责把内部消息转换成服务商需要的请求，并把响应转换回来。**执行循环**把回复和工具结果连接起来，控制继续与结束。**工具系统**负责访问文件、搜索内容和运行命令，同时返回明确的结果或错误。

只围绕这三个部分，就可以构建一个最小的任务执行闭环。

### 让任务保持连贯：上下文与会话

任务变长之后，需要决定每次给模型发送什么信息，并处理内容超过窗口的情况。这是**上下文管理**的职责。

任务还可能跨越多次启动，或者需要从某个位置重新尝试。**会话管理**负责保存历史、恢复状态和维护分支。完整记录保存在磁盘上，与每次请求包含哪些信息，是两个相关但不同的问题。

### 让系统可用、可控、可扩展

**交互层**让用户能够输入、观察进度、中断或补充要求。**权限与信任机制**控制项目资源的加载和工具动作的执行。**扩展机制**给新工具、命令与钩子提供接入位置。

有了单代理的基础，才能进一步讨论**子代理与并发**：怎样把任务交出去，怎样回收结果，以及多个代理修改同一份文件时怎么办。

**测试与评估贯穿这些模块。** 测试检查程序在特定条件下是否正确，真实任务验证它与模型配合后的表现，审查则帮助发现遗漏的需求与边界。

## 现在的 imp 做到了哪里

截至本文整理时，imp 已实现终端交互与单次任务模式，具备文件读写、搜索、Shell 命令、会话恢复与分叉、上下文压缩、扩展和子代理等能力。模型接入已覆盖 Anthropic、OpenAI 兼容协议、ChatGPT 订阅接入和 Z.ai；部分子任务可以在独立 Git worktree 中运行。

这些能力并不意味着所有边界都已经解决。例如：

- worktree 分离的是工作目录和 Git 状态，Shell 仍能访问其他路径；它不等同于操作系统沙箱。
- 把旧历史整理成摘要，会改变后续请求携带的信息；摘要请求本身也受模型上下文窗口限制。
- 工具执行成功、测试通过和任务满足需求，需要分别判断。

项目计划还记录了 Skills 机制、JSON 事件流或 RPC 接入、扩展热加载等后续方向。本文将它们视为待探索事项；目前的系列先围绕已经有实现与开发记录的模块展开。

## 系列目录与阅读方式

这个系列面向有 Coding Agent 使用经验、希望理解其内部机制的读者。你不需要先写过 Agent；涉及伪代码时，会先交代它解决什么问题，再解释关键步骤。

除开篇外，每章围绕一个核心主题组织。内容较多时可以拆成上下篇，阅读顺序保持不变。权限和测试的基本要求会随相关模块一起出现，专章再做系统整理。

每章会尽量回答六个问题：

1. **为什么需要这个模块？** 从具体任务或故障开始。
2. **它在系统里处于什么位置？** 说明输入、输出和协作关系。
3. **最小实现怎样工作？** 给出原理和简化伪代码。
4. **我在 imp 中实际做了什么？** 记录实现步骤、方案选择和取舍。
5. **最小实现遗漏了哪些问题？** 结合真实故障解释后续改进。
6. **怎样验证，以及还有哪些局限？** 用源码、测试、提交和执行记录支持结论。

伪代码用来抓住机制，关键 diff 与提交用来说明真实变化。涉及运行状态的章节，还会用可逐步查看的演示帮助理解，并明确区分模拟数据与真实记录。
