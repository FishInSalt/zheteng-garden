向 Coding Agent 提出“修好这个问题”的要求后，它就可能开始找文件、改代码、跑测试。模型回复之后，是谁在安排下一步？

AI 模型的能力越来越强，围绕模型搭建的工具也让不少工作变得更高效。我开始参考 [pi](https://github.com/earendil-works/pi)，从零开发 **imp**。pi 是一个支持自定义和扩展的终端编程助手。

这个系列就拿 imp 的实现来拆解 Coding Agent。开篇先聊为什么要做、需要哪些模块，以及后面准备讲什么。

## 1. 为什么想自己做一个 Coding Agent

我用过一些现成的编程助手。它们能做很多事，但用下来，总有些地方不太合自己的习惯。

对我这样的国内用户来说，Claude Code 的使用门槛让我觉得不够友好。用 Codex 时，我又希望看到更多推理过程，产品提供的展示没有完全满足我的需求。我接触到的一些国产工具，有的设计大量沿用一线产品，有的实现还比较简陋，暂时没找到特别合意的。

这些不顺手的地方，让我开始关注 Coding Agent 中的 **harness 层**。它负责把模型、工具、上下文和任务状态组织起来：给模型提供需要的信息，执行模型提出的工具调用，再把执行结果交给模型，让任务能够继续进行。模型与这层软件配合，构成我们使用的 Coding Agent（下文简称 Agent）。

我想通过开发 imp，理解这些模块的实现，也做一个更符合自己使用习惯的编程助手。这个系列会逐个介绍这些模块的原理和实现方式。

对于模型的推理内容，Agent 能展示多少，取决于模型服务返回了什么。工具调用、执行结果和发送给模型的上下文，则可以由 harness 记录，再通过交互层展示给用户。

## 2. 为什么选择 pi 作为参考

pi 吸引我的地方，是核心设计简洁，也方便按自己的需要增加功能。我想先理解一个编程助手的基本实现，再考虑加入会话、交互和扩展等功能。

做 imp 时，我先让模型能调用工具、拿到结果。之后每增加一部分，都先想清楚它要解决什么问题。

这里说的“从零开发”，指自己实现运行逻辑、工具和状态管理，并不意味着所有东西都重写。比如我用 TypeScript 和 Node.js 开发 imp，终端 UI 复用了 pi 的组件库。讲到相关章节时，会交代哪些部分自己实现，哪些部分复用了现成组件。

## 3. 一个任务是怎样跑起来的

假设项目中的求和函数执行 `sum(2, 3)` 时返回了 `23`，预期结果是 `5`。我们交给 Agent 这样一个任务：**“找到求和结果错误的原因，修复函数，并运行相关测试。”**

在这个例子中，我们还没有告诉模型函数写在哪，也没有提供测试结果。下面的流程图展示一次请求怎样变成多次模型调用：有工具请求，就执行并带着结果继续；没有工具请求，就显示回答并结束。本图只说明基本流程，并非真实运行记录。

比如模型请求读取文件，读取工具负责打开文件并返回内容；执行循环把这个结果放进消息历史，再次调用模型。接着，模型可能要求修改函数、运行测试。测试失败时，错误输出也会加入历史，供它继续判断。

一次 Agent 运行往往包含多次模型调用。**Agent Loop（执行循环）** 负责串起这些步骤：调用模型、执行工具、记录结果，再判断是否继续。01 章会用更小的“读取 README”场景，逐步介绍执行循环的实现。

## 4. 开发一个 Coding Agent，需要哪些模块

沿着刚才的任务，可以把 harness 层的主要工作分成下面几部分。模型通过模型接入层与这些模块配合。这张图按职责分组，源码里的一个文件或类不一定对应一个方框。

<AgentArchitecture />

### 4.1 模型接入、执行循环与工具

**模型接入**负责向模型服务发请求，把返回的数据转换成 执行循环使用的统一消息格式。不同服务的消息格式、工具调用和流式响应可能不同，需要在这里处理。

**执行循环**决定拿到回复后做什么：有工具请求就执行，把结果加入历史后再次调用模型；没有工具请求，或达到停止条件，就结束本次 Agent 运行。

**工具系统**负责实际操作文件和运行命令。模型发来一个“读取文件”的请求，打开文件的是工具代码；它还要处理路径、参数和读取失败的情况。

把这三部分接起来，再接入模型服务，就能运行一个最小 Agent。

### 4.2 上下文与会话

任务一长，消息历史就会不断增长。**上下文管理**要决定每次给模型发送哪些信息，放不下时删减或压缩什么。摘要可能丢失细节，不能只看它省了多少 token。

如果关闭 Agent 后，下次启动时还想继续任务，或者想从某条消息另开一个分支，就需要**会话管理**。它负责保存和恢复历史；**上下文管理**则决定本次请求要把哪些信息发给模型。

### 4.3 交互、权限、扩展与协作

**交互层**负责接收输入、显示执行进度、处理停止和追加要求。

**权限与信任机制**负责检查项目中的指令文件是否可信、工具操作是否被允许。**扩展机制**让用户能增加新工具、命令，或者在运行过程中执行自定义逻辑。

通过**子代理机制**，主 Agent 可以把子任务交给其他 Agent 单独处理，再收回结果。如果多个 Agent 同时工作，还需要处理**并发协作**：各自能看到什么上下文，结果怎样返回，同时修改文件会不会冲突。

**测试与评估**会贯穿这些模块。工具按预期执行了，并不代表 Agent 完成了用户的任务；除了检查代码逻辑，也要用实际任务验证效果。
