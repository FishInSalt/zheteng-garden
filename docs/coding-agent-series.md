# Coding Agent 原理与实践：写作与展示约定

## 目标、读者与作者背景

本系列以原理教学为主：让有 Coding Agent 使用经验的读者理解各模块如何工作，以及实现时需要处理哪些问题。imp 源码作为解释原理的实例，不按提交历史记录开发流水账。

作者提供的背景：模型能力提升，harness 让模型参与实际工作；现有产品在使用门槛、过程可见性、设计与完成度上未满足自己的偏好。pi 的简洁和自定义能力吸引了作者，因此参考 pi，从零实现自己的编程助手，既学习 Agent 的原理，也希望用它解决真实问题。

写作时保留作者的观点与声音。对 Claude Code、Codex 和国产产品的评价明确属于个人使用体验，不扩写成普遍事实；显示模型已返回的信息，不等于能够取得模型未提供的内部推理。

## 组织原则

- 章节按理解与实现的依赖关系组织，以最小执行闭环为起点。
- 每章按“小场景 → 带注释的源码节选 → 模拟运行 → 异常处理”展开，不以提交、里程碑或作者开发过程串起正文。
- 00 交代背景、整体架构和目录；不放开发时间线、提交列表、当前功能清单或未来功能计划，项目现状由仓库文档维护。01 用源码节选解释循环；02、03 分别拆开模型接入与工具实现。
- 04 讨论本次请求携带什么；05 讨论历史如何保存和恢复，明确上下文与持久化的区别。
- 权限与测试从相关模块开始出现，07 和 10 专章系统整理。
- 不按“核心程度”硬排序，也不将提交日志直接拆成博客。

### 上下篇拆分原则

- 不以字数作为唯一标准。若一篇需要解释多个相对独立的机制、不断引入新概念，或需要多段大型源码和多个演示才能讲清，应评估拆分。
- 按知识依赖和完整问题划分，每篇都应有明确的问题、完整的解释过程和可总结的结论，不能把同一段核心流程或对应异常处理生硬截断。
- 模块章拆分后仍围绕场景、核心源码、模拟和相关异常展开；异常跟随所属机制，避免统一堆到下篇。上下篇之间只保留必要的回顾与过渡。
- 拆分时保留原章节编号，并用“上／下”和具体题目区分，明确阅读顺序，同步文章导航与篇间链接。
- 第 02 章可评估以“请求转换与统一消息”和“流式接收、组装与中断”为两个完整问题，但目前只是候选方案，待内容展开后决定，不预先强制拆分。

## 单章模板

1. 小场景：先给一个读者熟悉的任务，让模块有具体的使用背景。用自然语言说明任务如何推进，数据结构、协议字段和接口名留到源码部分，先交代用途再展示。
2. 源码与原理：先展示精简的核心源码，用中文注释标出执行步骤、重复关系和停止条件，再按步骤分节分析。开头提示读者先看整体流程，不必立即理解每个参数；数据结构在对应小节解释用途。保留 imp 源码的主要语句和命名，明确省略了什么，不把改写稿标成完整源码。局部只节选当前分析需要的代码，文末不再重复整段循环。核心代码保留计数、上限和中断的真实检查位置与停止原因，长分支可以明确省略并指向异常小节。第四节对应这些位置解释处理原因；循环篇只解释工具错误怎样进入历史，不展开工具内部校验、权限检查或 try/catch 实现。中断后的结果补齐属于循环职责，需要保留。
3. 模拟运行：联动执行位置、输入输出和状态；预设数据明确标注模拟。
4. 异常处理：讲清触发条件、处理方式和需要保留的状态，必要时继续展示源码。

文章保留系列编号；模块章主体用 `1.` 至 `4.`，子节用 `2.1`、`4.1` 等。01 增加第 `5.` 节简短收尾，概括循环职责并衔接下一篇，避免在异常处理末尾重复引出下一篇；文章 01 文末不再渲染完整系列目录，章节导航由侧栏提供。00 作为导读按内容编号 `1.` 至 `6.`，架构子节用 `4.1` 至 `4.3`，不强套模块章的四步模板。直接从场景进入，不堆砌写作目标、抽象总结或反复强调的结论。用具体动作解释原理，少用“闭环”“边界”“关键是”等泛化措辞；不虚构作者经历。不在正文堆提交哈希、里程碑、测试数量与开发复盘。实现依据留在内部素材笔记，文章按需要链接源码。

## 表达检查约定

- 开发动机集中说明一次，避免在开头、正文和总结反复列同样的目标。
- pi 等参考项目首次出现时先交代是什么；图示和目录也采用读者能理解的表述。
- 原理部分优先使用通用概念：完整助手称 Coding Agent（语境明确后简称 Agent），组织执行的软件层称 harness，具体职责用执行循环、模型接入层、工具系统等模块名。imp 只用于作者背景、源码来源和具体实现取舍，不用项目名代替通用原理。
- 介绍执行循环时保留输入准备和输出去向：用户消息在哪里写入、工具怎样查找、模型回答怎样展示。区分事件驱动的显示、完整消息的保存和函数返回的运行状态，不能把停止状态写成回答正文。循环篇用简短文字说明回答经事件回调交给交互层展示，保留核心代码中的输出接口；事件转发链路和终端渲染实现留到交互篇，不在循环篇展开。省略流式显示的演示需注明范围。
- 区分一次模型调用与一次 Agent 运行；不要用“程序”含糊指代已有明确名称的对象。`turns` 等计数器先说明计数对象，演示使用“模型回复 N 次”；运行正常结束不等于任务已经验证通过。
- 内部消息和事件首次出现时说明来源，不让读者误以为是通用 API 格式。源码节选保留主要调用与状态变化，用明确的省略标记移除无关参数；注释须核对函数实际职责。避免写入易过时的默认配置值。
- 模拟演示与正文使用相同的任务场景，说明按主要动作推进、跳过部分判断。中断示例若依赖工具顺序执行，要写清前提。
- 模型推理内容的可见性取决于服务返回的信息，工具执行和上下文记录由 harness 管理，不混为一谈。
- 00 的例子写清现象与预期，并标为教学示意；先解释模块用途，worktree、沙箱、事件钩子等细节留到专章。
- harness 首次出现时说明它与模型共同构成 Agent；用户视角的使用与展示称 Agent，软件职责称 harness，具体动作优先用模块名。子代理是受委派的 Agent，委派与回收由主 Agent 组织。
- 第 3 节使用静态流程图：记录任务 → 调用模型 → 记录回复 → 判断工具请求；“是”分支执行工具并记录结果，从右侧返回模型调用，“否”分支从左侧到显示回答并结束。节点只写动作，模块职责留给架构图。中断、轮数上限和模型错误用图下注明，01 再展开。流程图无需 JavaScript，文字保持可选择，并提供完整的无障碍流程说明。

## 展示与技术约定

采用 MDX，保留 Markdown 正文，组件实现与文章分离。继续使用现有 Astro 和静态部署，不增加在线模型调用或新的前端框架。

### 视觉方向：可阅读的工程手记

- 连贯的单栏正文；图示只出现在解释结构或状态的位置。
- 图示使用局部色板：暖灰画布 `#eee8dd`、浅米白 `#fffcf6`、正文 `#343137`、辅助文字 `#706971`、执行紫 `#7150a3`、结果绿 `#087c6e`；深色主题提供对应颜色。
- 系统中文无衬线字体用于正文和注释，等宽字体只用于代码、哈希等精确信息。
- 架构图用边界表达职责，紫色突出执行中心，绿色用于工具与环境反馈。
- 架构图的每个模块使用独立的闭合边框和卡片底色；运行程序外框与内部模块保持层级差异。上下文、会话、权限、扩展分别展示，分组仅说明职责，不暗示执行先后；窄屏按图示容器宽度切换纵向排列。
- 不增加自动播放动画。手机上结构图转为纵向，正文和图注不依赖悬停。
- 静态文字承担完整解释；交互只帮助观察变化，不把核心结论藏在点击或视频中。

已评估课程落地页、仪表盘和工程手记三种方向：选择工程手记，因为本系列以长文解释和源码解释为中心。用户随后选择 Josh Comeau 为布局参考，并要求全站浅色主题改用暖米色；以文末的选定方案为准。

### 分三层制作

1. 正文、伪代码、表格和静态结构图先完成；图示保持可选择、可检索的文字。
2. 对循环、压缩、分支等动态机制，按文章需要制作一个目标明确的交互组件。
3. 按需用真实日志、文件修改前后对照和录屏辅助解释；长内容提供摘要、说明或文字稿。提交记录留在内部素材笔记中查证。

00 使用三个静态 Astro 组件：`AgentArchitecture`、`TaskOverview`、`SeriesDirectory`。采用语义 HTML 与 CSS 实现响应式图示，避免把手机上的文字缩进一张过宽的图。暂无必要引入 Mermaid 运行时；后续复杂时序图可评估构建时生成 SVG。

共用色板放在 `src/components/series/series-visual.css`，选择器限定在 `.series-visual`。后续交互优先用组件中的小段脚本，需要复杂状态时再评估框架。
